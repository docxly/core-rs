# 자주 묻는 질문

## 이 프로젝트는 어떤 사용자에게 적합한가

`docxly`는 서비스나 브라우저 안에서 문서를 직접 생성해야 하는 팀에 맞습니다.
CLI 중심 변환 파이프라인이 핵심이라면 Pandoc이 더 잘 맞을 수 있습니다.

## 가장 먼저 어떤 경로로 시작해야 하는가

가장 안전한 시작점은 npm DOCX입니다.

- Node 서비스: `generateDocx`
- 브라우저 제품: `generateDocx` + 번들러
- Rust 통합: `generate_docx`

## HWPX를 현재 도입해도 되는가

쓸 수는 있지만 베타로 보는 것이 맞습니다.

- npm과 Rust 모두 HWPX API가 있습니다.
- 다만 DOCX보다 지원 범위가 좁습니다.
- 승인 fixture 기준 밖의 동작은 보수적으로 검증해야 합니다.
- 공개 npm 옵션은 현재 `title`, `author`, `strictMode`까지만 제공합니다.

## 브라우저에서 바로 `<script type="module">`로 사용할 수 있는가

아니요. `.wasm` 자산을 처리할 수 있는 번들러나 런타임이 필요합니다.

## 성능 수치는 어떻게 해석해야 하는가

숫자 자체보다 재현 가능성이 더 중요합니다.

- [성능 비교와 포지셔닝](./benchmark.md)에 있는 명령으로 다시 측정할 수 있습니다.
- 브라우저 실측이 아니라 오프라인 Node 기준이라는 점을 같이 봐야 합니다.

## 출력이 예상과 다를 때 무엇부터 확인해야 하는가

1. 입력 Markdown이 현재 지원 범위 안인지 확인합니다.
2. Strict Mode에서 오류가 나는지 확인합니다.
3. 실제 생성 파일을 열어 봅니다.
4. fixture나 golden 산출물과 비교합니다.

특히 HWPX는 XML만 보지 말고 실제 렌더링 결과를 같이 보는 편이 맞습니다.

## 이슈와 기능 요청은 어떻게 구분해야 하는가

- 문서화된 동작과 실제 결과가 다르면 버그 이슈
- 새로운 출력 기능이나 더 넓은 지원 범위가 필요하면 기능 요청
